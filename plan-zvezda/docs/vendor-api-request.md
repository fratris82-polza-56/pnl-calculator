# Запрос разработчикам «АйТи какая! Аптека» (itwhat.ru): передача данных о продажах

> Готовый текст для отправки в техподдержку/отдел продаж вендора (поддержка
> 8:00–20:00 МСК, документация у них только для клиентов из самой программы).
> Ключ интеграции (X-Intg-Key) передать отдельно защищённым каналом — не
> включать в письмо.

---

Тема: Запрос на интеграцию — автоматическая передача данных о продажах во внешнюю систему

Добрый день!

Мы используем «АйТи какая! Аптека» в сети из 5 аптек. Просим передавать данные
о продажах из вашей системы в нашу аналитическую систему «План-звезда»
(план/факт по сотрудникам и аптекам). Судя по описанию, у вас уже есть всё
необходимое: планировщик задач (выгрузка по расписанию), выгрузка отчётов
в CSV/XML и работа с FTP — просим подсказать штатный способ и настроить его.

## Вариант А (предпочтительно): push — POST по расписанию

Ваш «Планировщик задач» раз в сутки (после закрытия смены/Z-отчёта) отправляет
HTTP POST с JSON:

**Endpoint:** `POST http://zvyagin-ai.polza.ru:8080/api/integration/sales`
**Заголовок:** `X-Intg-Key: <ключ — передадим отдельно>`
**Формат:** JSON, кодировка UTF-8.

```json
{
  "pharmacy_id": 1,
  "sales": [
    {"doc_id": "Ч-1042", "d": "2026-09-29", "employee_name": "Иванова Анна Сергеевна", "amount": 1250.50, "margin": 310.20},
    {"doc_id": "Ч-1043", "d": "2026-09-29", "employee_name": "Иванова Анна Сергеевна", "amount": 840.00, "margin": 196.40}
  ]
}
```

**Поля:**

| Поле | Обяз. | Описание |
|---|---|---|
| `pharmacy_id` | да | Код аптеки: 1 — Азовская, 2 — Юбилейный, 3 — Проспект Мира, 4 — Маяковская, 5 — Пятницкое (согласуем под ваши внутренние коды) |
| `sales[].doc_id` | нет | Номер чека. Нужен для защиты от дублей: повторная передача строки с тем же `doc_id`+дата+аптека пропускается без задвоения. Без `doc_id` строки считаются сводкой дня и ЗАМЕНЯЮТ итог дня сотрудника |
| `sales[].d` | да | Дата продажи, `ГГГГ-ММ-ДД` |
| `sales[].employee_name` | нет | ФИО продавца/провизора, как в кадровых данных (полностью, не инициалы) — мы сопоставляем без учёта регистра и лишних пробелов |
| `sales[].amount` | да | Сумма строки/чека в рублях |
| `sales[].margin` | нет | Валовая прибыль (наценка) по строке. Если не считаете — передавайте закупочную цену, согласуем |

**Одна партия = одна смена/день одной аптеки.** Допустимо слать и построчно чеки
(тогда с `doc_id`), и итоги по сотрудникам за день (тогда без `doc_id`).

**Периодичность:** раз в сутки после закрытия смены (снятия Z-отчёта) за прошедший
день. При недоступности нашего сервиса — повторные попытки до успеха.

**Ответ нашей системы:**

```json
{"ok": true, "accepted": 120, "duplicates": 3, "mapped": 117, "unmapped": ["Петров П.П."]}
```

`unmapped` — ФИО, не сопоставленные с нашим справочником: мы их сохраним и
разберём вручную, дублирования факта не произойдёт.

**Ретроспектива:** после настройки просим одной (или помесячной) выгрузкой
передать продажи с 01.09.2026 — заполним факт по плану Q4.

## Вариант Б: мы забираем сами (pull) — штатные механизмы вашей системы

1. **Отчёт по расписанию в CSV/XML** (ваш конструктор отчётов + планировщик,
   выкладка на FTP или в сетевую папку): отчёт «продажи по сотрудникам за день»
   с полями дата, номер чека, ФИО сотрудника, сумма, наценка. Пришлите макет —
   адаптируемся под ваш формат и будем забирать сами.
2. **Прямой доступ к PostgreSQL** (если проще для вас): read-only пользователь
   и представление (view) с продажами по кассирам — забирать будем сами,
   нагрузку согласуем (ночной опрос).

## Технические детали нашей стороны

- Приёмное API уже работает и протестировано; повторная передача партии
  не задваивает факт (защита по номеру чека `doc_id` + дата + аптека).
- Нераспознанные ФИО не теряются: сохраняются и разбираются вручную.
- По сотрудникам нужен ФИО полностью (без инициалов) либо ваш внутренний
  код сотрудника — согласуем сопоставление.
- Наш сервис доступен по внутренней сети/интернету; при недоступности
  планировщик должен повторять отправку до успеха.

## Что просим от вас

1. Подтвердить, какой вариант реализуем штатно (POST из планировщика,
   CSV/XML-выгрузка, FTP, доступ к PostgreSQL) и что нужно с нашей стороны.
2. Тестовую партию за один закрытый день по одной аптеке — проверим
   сопоставление ФИО и итоги в тот же день.
3. Ретроспективу продаж с 01.09.2026 одной выгрузкой (или помесячно) —
   заполним факт по плану Q4.

Ключ интеграции передадим защищённым каналом после согласования формата.
